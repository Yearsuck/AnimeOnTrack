# Plan 2026-10-30: Android version (feasibility + phased plan)

Source: Claude research subagent (sonnet), read-only. Spot-checked by the supervisor: scraper `eval()` is
`#[cfg(windows)]` with a not-windows stub (`scraper_engine.rs:696`), WebView2 deps are Windows-only
(`Cargo.toml:56-58`), updater registered without a desktop gate (`lib.rs:115`), Drive OAuth uses a
`127.0.0.1` loopback listener (`backup/oauth.rs:227`).

## Verdict
Worth it as a **tracking/catalog app** or a **companion to the PC app**; a full port with the scraper is the
least advisable (large effort, Cloudflare risk in Android System WebView unverified, Play Store would
reject an app that links pirate streaming sites -> APK sideload via GitHub Releases only).

## Per-subsystem
- Works as is (pure Rust): SQLite, AniList catalog, matching, stats, recommender, swipe, cover cache (check asset scope).
- Port: scraper (Kotlin plugin, offscreen `WebView` + `evaluateJavascript`), ad block (`shouldInterceptRequest`),
  player (external browser or ExoPlayer), SecureStore (Android Keystore; today non-Windows stores plaintext),
  OAuth (deep link / Android client instead of loopback), downloads to public storage (MediaStore/SAF).
- Drop on mobile: updater (desktop-only plugin), UI watchdog, Defender/MOTW quarantine, custom title bar, explorer.

## Phases
0. **Spike (S)**: minimal Tauri Android app + Kotlin plugin; offscreen WebView loads each site, reads
   `document.title`/HTML via `evaluateJavascript`; measure Cloudflare pass rate on 2-3 devices. Decides phase 4.
1. **Base port (M)**: `tauri android init`; `cfg(desktop)` gates for updater/process/watchdog/window controls;
   DB + AniList + stats + swipe running; Keystore-backed secrets.
2. **Mobile UI (M)**: touch layout, bottom navigation, no shortcut dependence, 3D graph reduced or optional.
3. **Sync with PC (M)**: incremental sync over the existing Drive backup (today whole-DB restore only):
   seen state merge, PC keeps scraping. OAuth via deep link.
4. **Only if the spike passes: Android scraper (L)**, adblock via `shouldInterceptRequest`, player in browser.

## Phase 2a: back button and mobile behaviour (user request 2026-10-30)
Found: navigation is React state only (`App.tsx:113` `view`), no history entries, so Android "atrás" has nothing to
go back to and closes the app from any screen. Tauri's generated `WryActivity.kt:62` calls `webView.goBack()` when
`canGoBack()`, else finishes the activity. `@tauri-apps/api/app` 2.11 also exposes `onBackButtonPress`.

Design: one back stack in `src/lib/backStack.ts` on top of the History API (works with Tauri's default handler, and gives
desktop mouse "back" for free). `useBackLayer(open, close)` pushes a history entry when an overlay opens and closes
it on `popstate`; closing by UI pops the entry. Order of what "atrás" closes, top first:
1. menus / dropdowns (`components/Menu.tsx`), filter drawer (`catalog/FilterDrawer.tsx`), deck panel (`Descubrir/DeckPanel.tsx`),
   list toolbar popovers (`listas/ListasToolbar.tsx`), maintenance dialogs (`settings/MaintenanceSection.tsx`), graph node menu (`StatsGraph.tsx`);
2. sheets and dialogs: `AnimeSheet`, `ShortcutsOverlay`, `Tutorial`, `LaunchOverlay`, the series detail;
3. sub-tabs (Stats resumen/grafo/generos, Descubrir sections) back to their first tab;
4. main view back to the home view (Pendientes); 5. at home: exit (Android default).
Every overlay already closes on Escape: reuse the same close callbacks.

Tests: Vitest for `backStack` (push/pop order, UI close pops its entry, no double pop, reload safe); on the phone
(only with the user's OK, the phone is theirs): checklist below.

Mobile checklist to run on the device: back from every overlay/view (list above); app to background and back
(timers, refresh in progress, player window); kill from recents and reopen (DB intact, last view); rotate; on-screen
keyboard over search inputs; safe-area / notch insets; hover-only controls reachable by tap; long lists scroll;
external links open in the browser; the empty title-bar gap (`App.tsx:468`, `:545`).
